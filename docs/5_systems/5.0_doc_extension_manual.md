# 5.0 Руководство по расширению документации

**Принцип:** Документация должна быть настолько детальной, чтобы по ней можно было поставить техническую задачу и реализовать систему в коде.

### Обязательная структура системы

```markdown
# X.X Название системы

**Определение:** Краткое описание назначения системы

### Базовые концепции
- Ключевые термины и их определения
- Основные структуры данных

### Техническая реализация
- Как система работает (компоненты Unity, ScriptableObjects, корутины и т.д.)
- Алгоритмы и процессы
- Жизненный цикл системы

### [API/События/Параметры] (опционально)
- Только если система предоставляет API другим системам
- Только реальные события, которые система генерирует
- Только runtime параметры, которые можно настроить

### Ограничения и особенности
- Архитектурные решения и их обоснование
- Текущие ограничения системы
```

### Что НЕ включать в документы систем

❌ **Интеграция с другими системами** - это описывается в механиках  
❌ **Расширяемость системы** - документируем текущее состояние  
❌ **Идеи для будущего развития** - не место для планирования  
❌ **Технические принципы** - если не несут практической пользы  
❌ **Абстрактные примеры использования** - только если система предоставляет API  
❌ **Параметры без конкретных значений** - только реальные настройки  

### Хорошие примеры разделов

✅ **Корутинная архитектура системы ходов** - описывает реальную реализацию  
✅ **ScriptableVariable в GridMap** - показывает как работают динамические изменения  
✅ **MapRegistry API** - конкретные методы с сигнатурами  
✅ **События системы ходов** - что система триггерит для других систем  

### Принципы написания

**Техническая конкретность:**
- Описывайте реальную архитектуру, не абстрактные концепции
- Указывайте конкретные структуры данных, API, алгоритмы
- Для нереализованных систем - детальное техническое задание для программиста

**Независимость систем:**
- Системы независимы по умолчанию
- Если система использует артефакты другой системы - явно указывайте какие и зачем
- Обосновывайте каждую зависимость между системами

**Артефакты и интерфейсы:**
- Четко описывайте что система производит (события, API, данные)
- Указывайте что система потребляет от других систем
- Описывайте интерфейсы взаимодействия

**Практическая реализуемость:**
- Каждая описанная функция должна быть технически реализуема
- Избегайте неопределенных формулировок типа "система поддерживает..."
- Конкретные алгоритмы, структуры данных, жизненные циклы

### Примеры плохой документации

❌ **"Система поддерживает интеграцию с другими системами"** → указать конкретно с какими и через какие артефакты  
❌ **"Система для управления инвентарем"** → описать структуры данных, API, алгоритмы  
❌ **"Параметры настройки системы"** → указать конкретные параметры и их назначение  
❌ **"Система использует события"** → какие события, когда генерируются, кто подписывается  

### Примеры хорошей документации

✅ **"Система генерирует событие OnTurnEnd после завершения корутины актора"** → конкретное техническое описание  
✅ **"MapRegistry.GetCellProperty(Vector2Int coordinates, property)"** → точная сигнатура API  
✅ **"Свойства хранятся как ScriptableVariable<bool> для динамических изменений"** → техническое решение с обоснованием  
✅ **"Система потребляет события системы ходов для обновления счетчиков состояний"** → четкая зависимость с обоснованием

### Процесс работы с документацией

**Для планируемых систем:**
1. Начните с определения назначения системы
2. Опишите техническую архитектуру (структуры данных, алгоритмы)
3. Определите артефакты системы (что производит, что потребляет)
4. Обоснуйте зависимости от других систем
5. Убедитесь, что документ может служить техническим заданием

**Для реализованных систем:**
1. Опишите реальную архитектуру и процессы
2. Зафиксируйте API и параметры системы
3. Документируйте текущие ограничения
4. Обновляйте при изменении реализации

**Валидация документа:**
- Можно ли по документу реализовать систему с нуля?
- Все ли зависимости от других систем обоснованы?
- Описаны ли конкретные артефакты (API, события, данные)?
- Нет ли неопределенных формулировок?
